§3.104  BASIC AUTH — six points
========================================================================

POINT 1 — a URI / method / protocol / processing path outside the 8 (now 9) blocks, or answered
          before the access phase?
  CLEAN AT THE NGINX LAYER. I could not construct one.
   - location / is the catch-all; auth_basic runs in the ACCESS phase, which executes for proxied
     and for static (alias) content alike — static files are served in the content phase, AFTER access.
   - nginx normalises the URI (%xx decode, /../ collapse) BEFORE location selection, so encoding
     tricks (/%2e%2e/, /./) cannot dodge a block; GELB measured 400/401 for these.
   - = / ^~ / regex precedence: every terminal selection lands in a block that carries auth. The
     exact block (= /api/pdf) and the regex block (~* \.pdf$) are both auth'd; a miss on the exact
     block falls to /api/ or / which are auth'd.
   - HTTP/3 (QUIC) is NOT configured (listen 443 ssl only), so there is no unauthenticated h3 endpoint.
     HTTP/2 measured 401.
   - Next.js internal paths — /_next/static, /_next/image?url=, /_next/data, Server Actions (POST /),
     websocket upgrade — all route through location / (block 8/9) under auth. (Note: /_next/image?url=
     is an SSRF/open-proxy surface AFTER auth; not an auth bypass, flagged for later.)
   - No error_page redirect, X-Accel-Redirect/internal location, named location (@x), or try_files is
     configured, so none of the classic pre-access content paths exists.

  THE REAL BYPASS IS BELOW NGINX, and it is a MEASUREMENT, not logic:
     Basic Auth exists only on the reverse proxy (:80/:443). The app (:3003) and backend (:8002)
     listen on their own ports. GELB's checks "App direkt :3003 200, Backend direkt :8002 /health 200"
     were run ON the server (localhost); they prove the listeners exist, not that they are unreachable
     from the internet. If either binds a public interface AND the host/Hetzner-cloud firewall permits
     inbound, then
         http://<ip>:3003/...     and     http://<ip>:8002/...
     reach the app and backend with NO Basic Auth — a complete bypass of all 9 blocks. This is also
     where the §3.103 proxy-token exposure is or is not closed: /api/admin/proxy is only auth'd at
     :443; a direct hit on :3003/api/admin/proxy/<x> still wields BACKEND_TOKEN.
     REQUESTS THAT DEMONSTRATE IT, run from OFF the server:
         curl -ksS https://<ip>:3003/api/admin/proxy/health
         curl  -sS http://<ip>:8002/health
     If either returns content, the gate is void for that path.
     MEASUREMENTS REQUESTED FROM GELB:
         ss -ltnp | grep -E ':3003|:8002'      (bind address: 127.0.0.1 vs 0.0.0.0)
         host firewall / cloud firewall inbound rules for 3003 and 8002
     VERDICT point 1: CONDITIONAL GO — clean at nginx; GO iff :3003 and :8002 are not externally
     reachable.

POINT 2 — per-location auth vs server-wide auth + explicit ACME exception: improvement or gap?
  GO on correctness, WITH DISSENT.
   - Renewal concern VALIDATED (see point 3): certbot 2.9.0 inserts `location = /.well-known/
     acme-challenge/<token>` (exact match, highest precedence). Server-wide auth_basic is inherited
     into every location INCLUDING a certbot-inserted one, so it would have 401'd the challenge.
     Per-location auth is not inherited, so the inserted exact-match block stays open. GELB's mechanism
     is correct.
   - DISSENT: per-location auth is FAIL-OPEN — any future location added without auth_basic (by a
     later edit, an include, a new app route needing its own block) is unprotected by default. A
     security gate should fail CLOSED. The alternative that achieves BOTH fail-closed AND renewal
     safety is: server-wide auth_basic + a PERMANENT `location ^~ /.well-known/acme-challenge/
     { auth_basic off; root <webroot>; }` using the --webroot authenticator (which writes a file into
     a static location and never live-inserts a location, so GELB's duplicate-location worry does not
     arise — that worry is specific to the nginx authenticator).
   - Net: GELB's choice is defensible given the proven renewal and the dev.syntx-system.com history,
     but it is a trade (renewal-robustness over fail-closed default), not a pure win. OTTAVIO should
     know that.

POINT 3 — does certificate renewal still work?
  CONFIRMED, now empirically (was: open). `certbot renew --dry-run` exit 0, "all simulated renewals
  succeeded", mechanism visible in the log (exact-match acme location inserted, ACME fetch over
  http://.../acme-challenge/<token>), vhost md5 unchanged after the run, cert valid to 2027-01-26.
  My earlier logical concern (the committed :443 config has no ACME exception, so renewal depends on
  certbot's transient live-insert) is answered: certbot performs exactly that insert and it succeeds.
  OPERATIONAL CAVEAT (GELB raised it): certbot.service is already `failed` because of
  dev.syntx-system.com's standalone authenticator (F-DEP-2). Ensure the admin cert's scheduled renewal
  is not collateral-blocked by that failing unit (a successful --dry-run for one cert does not prove
  the timer runs all certs).

POINT 4 — does `proxy_set_header Authorization ""` break anything unseen?
  CONFIRMED correct and necessary.
   - Without it nginx forwards the inbound `Authorization: Basic base64(condyn-admin:pw)` to the
     foreign :8002 app on every /api/ request routed there, landing the (trivially reversible base64)
     Basic credential in the foreign app's logs — a direct violation of Auflage 4. Stripping it is right.
   - What it breaks: only a client that relied on passing a Bearer token THROUGH nginx /api/ to :8002.
     GELB's "no such client in the logs" rests on access logs that record PATHS, not headers (a Bearer
     is a header), so that evidence is weak. The STRONG argument, which holds: the admin app never
     routes a client Authorization through that path — it reaches :8002 via CONDYN_API_URL=
     localhost:8002 directly (bypassing nginx), and /api/admin/proxy injects its OWN Bearer ${BACKEND_
     TOKEN} server-side (confirmed route.ts:40), independent of the client header. No internal consumer
     breaks.
   - Minor: "" sends an EMPTY header, not an absent one; equivalent for virtually all upstreams, only
     matters if :8002 distinguishes empty from missing. Negligible.

POINT 5 — can the change affect a foreign vhost? (admin is the :443 default_server)
  GO, with one check for GELB.
   - If admin.condyn.eu was ALREADY the :443 default_server, then IP / no-Host / unknown-Host requests
     hitting this block and now returning 401 is an IMPROVEMENT (unknown traffic is challenged, not
     served). It does NOT reach other vhosts: each foreign vhost matches its own server_name and is
     served by its own server block; auth_basic is confined to THIS block's locations. GELB's
     measurements corroborate (foreign hosts 200; shared /etc/nginx/.htpasswd untouched by md5+mtime).
   - CHECK: confirm `default_server` was PRE-EXISTING on this block's listen line and not newly
     introduced, and that no other :443 block claims default_server (nginx errors on a duplicate). The
     whole-file md5 changed (auth added), so the listen line cannot be diffed from the hashes given.

POINT 6 — what is still unprotected that should be protected? Is "bundle now behind auth" real?
  REAL improvement at the EDGE, but it is EDGE auth, not APPLICATION auth.
   - Real: the client bundle (its NEXT_PUBLIC_* literals) and the token-wielding /api/admin/proxy are
     no longer anonymously reachable through nginx; an unauthenticated internet client gets 401 first.
     That closes the anonymous-internet exposure of §3.103 point 6 — PROVIDED point 1 (direct ports)
     is clean. Not self-deception.
   - GAP (a): the new server-side gate /api/admin/session is consumed ONLY by ConDynPanel's UI-reveal
     GET (confirmed: the sole consumer of adminSessionIsOpen is the session route's GET). NO privileged
     route consumes the session — /api/admin/proxy/[...path] is unchanged and still injects BACKEND_
     TOKEN for anyone who reaches it. So at the APPLICATION layer the token-wielding proxy is
     authorised by nothing; the sole gate on it is nginx Basic Auth: one shared credential, no
     per-user accountability. Do NOT tell OTTAVIO the privileged API is behind the app login; it is
     behind Basic Auth only.
   - GELB's self-report (Basic-Auth user "condyn-admin" is a prefix of client user
     "condyn-admin-b28544"): for the Basic credential this is BELANGLOS — I agree (usernames are not
     secret; 24-char random password under bcrypt). But the printed fragment is a reminder that the
     OLD client-side admin credential shipped in a bundle historically; treat it as retired/compromised
     and ensure it is reused nowhere (it must not equal the Basic Auth password or any backend cred;
     GELB's Basic password is independently generated, so that is fine — just confirm the retired one
     is dead).

   server. (If you prefer one source of truth, set X-Forwarded-Proto $scheme once and repeat the full
   proxy_set_header set in every proxying location, since they do not inherit.)
